# G-Partner: витрина, CRM и запуск на BotHost

Версия решения: сентябрь 2026. Реализация рассчитана на один экземпляр
Python-приложения и небольшой/средний каталог одного магазина. Обещания
«миллиардной конверсии» и абсолютной неуязвимости не являются техническими свойствами.

## Что меняется для покупателя

На главной — магазин и город, фото, заметная кнопка каталога, поиск и текстовые
категории. В каталоге — только опубликованные владельцем товары, цены и
характеристики. Фильтры можно комбинировать и сбрасывать. Товар открывается
полноценной страницей; корзина сохраняет выбранные позиции, заявка оформляется
без обязательной регистрации. До заполнения настроек приём заявок отключён.

Поиск с кнопкой и видимые фильтры опираются на [мобильные исследования Baymard
2026](https://baymard.com/blog/mobile-ux-ecommerce). Немедленная видимость первого
экрана — на [кейс Nuvemshop](https://web.dev/case-studies/nuvemshop). Результаты
чужих магазинов не выдаются за прогноз роста G-Partner.

## Выбранная архитектура

| Слой | Реализация | Почему |
| --- | --- | --- |
| Витрина и CRM | React 19.2.8 + TypeScript 7.0.2 | Типизированный общий интерфейс ПК/телефона |
| Сборка | Vite 8.2.2, Node 24 LTS | Статическая сборка, в контейнере не нужен Node-сервер |
| Дизайн | CSS Grid/Flex, Montserrat/Inter локально | Малый набор зависимостей, чёткая типографика |
| Motion | GSAP 3.15.0, правила HyperFrames | Конечная световая проходка и отклик кнопки; reduced-motion |
| API/бот | Python 3.13, aiohttp 3.14.3, aiogram 3.31.0 | Сохранены `main.py` и `index.py`, один порт BotHost |
| Данные | SQLite WAL в `DATA_DIR` | Простая эксплуатация для одного экземпляра |
| Изображения | Pillow 12.3.0 → WebP | Проверка содержимого, лимиты, удаление метаданных |

Проверены также Three.js 0.185.1 и Tailwind CSS 4.3.3. Они не включены ради
галочки: 3D без подготовленных моделей не помогает выбору, а смена CSS-инструмента
не даёт сама по себе роста продаж. Для нескольких реплик потребуется PostgreSQL
и объектное хранилище, а не SQLite-файл на общей сетевой папке.
[SQLite: границы применения](https://www.sqlite.org/whentouse.html).

ИИ не получает пароль владельца, заявки или право публикации через открытый MCP.
MCP браузера применяется при разработке и тестировании. Готовая внешняя ИИ-интеграция
не заявляется: её нет без конкретного провайдера, ключей, согласованных данных и бюджета.

## Код без пропусков

Полные листинги находятся в репозитории, не в псевдокоде:

- `apps/mini-app/src/components/StoreHero.tsx` и `store-hero.css` — модульный первый экран.
- `apps/mini-app/src/storefront/` — каталог, товар, избранное, сравнение, корзина, заявка.
- `apps/mini-app/src/admin/` — кабинет владельца.
- `store_api.py` — серверная авторизация, фото, товары, настройки, заявки.
- `main.py`, `index.py`, `Dockerfile` — запуск сайта вместе с Telegram-ботом.
- `tests/` и frontend `*.test.*` — автоматические проверки.

Анимация Hero использует правила HyperFrames `ambient-glow-bloom` и
`press-release-spring`. Здесь это интерактивный React/GSAP-компонент, не фоновое
видео: таймлайн конечный, не сдвигает layout и не скрывает фото или CTA. Система
reduced-motion полностью отключает его. Не используется автокарусель, курсор-
ловушка или принудительная прокрутка.

## Настройка BotHost

1. Репозиторий `voglogpro/magoleg`, ветка `main`, Dockerfile из корня.
2. Сохранить прежние `BOT_TOKEN` и `MINI_APP_URL`. Токен бота не менять без необходимости.
3. `PUBLIC_ORIGIN` — полный HTTPS-origin магазина без пути, например домен,
   который вы уже используете в BotFather. `MINI_APP_URL` — HTTPS-ссылка магазина.
4. `ADMIN_USERNAME=megaolegshop2000`.
5. В секрет `ADMIN_PASSWORD` вставить заданный владельцем пароль. В коде,
   Dockerfile и GitHub его нет. Более безопасный вариант — выполнить
   `python scripts/admin_password.py` локально и задать полученный
   `ADMIN_PASSWORD_HASH` вместо `ADMIN_PASSWORD`. При смене секрета старые
   сессии перестают действовать после перезапуска.
6. `COOKIE_SECURE=true`; HTTPS обязателен. Кабинет лучше открывать обычным
   браузером, а не iframe Telegram Web: его встраивание намеренно запрещено.
7. **Использовать `DATA_DIR=/app/data`** — именно эту папку сохраняет BotHost
   согласно [официальной документации](https://bothost.ru/docs/database-storage).
   Проверить её наличие в файловом менеджере и сохранение после пересборки.
   Контейнер подготавливает права только своей папки данных и затем запускает
   сервис под UID 10001. Обычная папка вне постоянного хранилища не подходит.
8. Использовать порт, назначенный BotHost через `PORT`; сервер слушает `0.0.0.0`.
   Если порт не задан, используется 8000. `WEB_ONLY=false` для бота и сайта вместе.
9. Пересобрать контейнер; проверить `/health`, затем `/admin`.

Если папка `/app/data` в конкретной конфигурации не сохраняется после деплоя,
**не начинайте загружать боевой каталог**: сначала уточните настройку в поддержке.
Документация платформы подтверждает назначение папки, но не заменяет проверку
именно вашего развёртывания. Код и статика лежат вне `/app`, потому что BotHost
может монтировать туда исходники из Git. [Кастомный Dockerfile](https://bothost.ru/docs/custom-dockerfile).

Перед передачей доступа желательно заменить пароль, уже отправленный в переписке.
Не публикуйте его в README, issue, скриншоте кабинета или shell-команде.

## Первое заполнение CRM

Открыть `https://ваш-домен/admin` либо «Профиль → Вход для владельца».

1. Войти с настроенными учётными данными.
2. «Магазин и документы»: внести реальные контакты, адрес, часы, доставку,
   оплату, гарантию и сведения о продавце. Не переносить обещания конкурентов.
3. «Товары → Добавить товар»: имя, описание, тип, цена, наличие, характеристики.
4. Загрузить JPEG/PNG/WebP до 8 MiB. Сервер проверяет, что файл действительно
   изображение, ограничивает размеры и сохраняет новый WebP без метаданных.
5. Сохранить черновик. Чтобы покупатель увидел модель, включить публикацию.
   Для публикации нужны название, описание, фото и цена.
6. Категории «С правами / Без прав» указывать только после проверки документов
   модели; подтверждение в CRM обязательно. Не выводить правовой статус из одного
   названия или из рекламной мощности двигателя.
7. Проверить карточку с телефона, цену, характеристики и фото.
8. После проверки реквизитов и условий обработки контактных данных включить заявки.
   Сервер не разрешает включение без минимально необходимых настроек продавца и связи.
9. Заявки появляются во вкладке «Заявки»; владелец меняет статус после связи с клиентом.
   Фильтрация статусов выполняется на сервере; страницы по 50 записей позволяют
   открыть старые обращения, а не только последнюю тысячу.

Это заявки на согласование покупки, **не онлайн-оплата** и не интеграция с кассой.
Автоматическая отправка уведомлений менеджеру и платёжный провайдер в этот релиз
не включены. Заявки проверяются в CRM; не обещайте моментальный ответ без оператора.

## Безопасность и эксплуатация

Сервер проверяет каждый доступ к закрытому API. Пароль хешируется scrypt,
сессия хранится на сервере; cookie HttpOnly/SameSite/ Secure. Для изменений нужны
CSRF-токен и допустимый Origin. Включены ограничения попыток входа, размеров
запросов, загрузок и частоты заявок. Цены заявки пересчитываются на сервере.
Повторный запрос с тем же `Idempotency-Key` не должен создавать второй лид.

Ориентиры реализации: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).
Это меры защиты, не гарантия отсутствия всех уязвимостей. Нужны обновления,
мониторинг, резервные копии и периодический независимый аудит.

`X-Forwarded-For` от произвольного клиента не считается доверенным. На BotHost
лимиты могут видеть адрес общего прокси; это учитывается в границах приложения,
а защиту от большого бот-трафика должен обеспечивать также хостинг/edge.

Кабинет получает CSP с `frame-ancestors 'none'`, не загружает Telegram SDK.
Публичная витрина допускает Telegram Web. Только короткий стартовый процесс
подготавливает права allowlisted-папки данных; веб-сервер и бот работают не от root.
Секреты и данные исключены из Git и Docker build context.

### Резервное копирование

`python scripts/backup_store.py /путь-вне-data/gpartner-backup.tar.gz`

Указать новый файл, не существующий архив. Скрипт делает консистентный SQLite
backup и добавляет фото. Архив содержит персональные данные — ограничить доступ,
хранить защищённую копию вне BotHost. Для восстановления остановить приложение,
проверить доверенный архив, восстановить `store.sqlite3` и `uploads` в пустой
подготовленный DATA_DIR, проверить владельца UID 10001 и сначала провести проверку
на тестовом экземпляре. Не распаковывать неизвестные архивы и не затирать рабочие
данные без отдельного подтверждения. Автоматическое расписание backup не настроено.

## Проверка перед открытием продаж

- [ ] Секреты заданы в BotHost, `/admin` не пускает без входа.
- [ ] Данные и фото пережили именно пересоздание контейнера, не только restart.
- [ ] Реальные контакты и документы проверены владельцем/специалистом.
- [ ] Тестовый товар проходит черновик → публикация → поиск → корзина → заявка.
- [ ] Тестовая заявка видна владельцу и её сумма правильная.
- [ ] Мобильный экран, клавиатура, фильтры и кнопки проверены на устройствах.
- [ ] Резервная копия создана, копия вынесена за пределы сервера, восстановление проверено.
- [ ] Настроено наблюдение за ошибками, диском и новыми заявками.

Цели скорости: LCP ≤2,5 s, INP ≤200 ms, CLS ≤0,1 на 75-м процентиле реальных
пользователей — [официальные Web Vitals](https://web.dev/articles/vitals).
Локальная сборка и браузерный smoke-test не доказывают эти показатели на BotHost.
SEO карточек через hash-навигацию ограничено: отдельные индексируемые URL с SSR/SSG
и sitemap — следующий этап перед масштабной органической рекламой.

## Проверки разработчика

Проверка релиза 06.09.2026: чистый `npm ci --ignore-scripts`, production-сборка,
38 frontend-тестов и 41 Python-тест прошли локально. Браузерный прогон витрины
с контролируемыми API-ответами: 159 утверждений, ширины 320/390/768/900/1440.
Отдельно на настоящем локальном API проверен путь: вход владельца → загрузка
фото → публикация → корзина → сохранённая заявка → изменение статуса в CRM.
Тестовые данные изолированы и не включены в репозиторий. Проверка CRM на телефоне
не выявила горизонтального переполнения и ошибок в консоли.

`npm audit --omit=dev`: известных уязвимостей production-зависимостей не найдено
на дату проверки; это не полноценный аудит всего приложения. Локальное окружение —
Windows/Python 3.11; Python 3.13 и реальный Linux-контейнер проверяются отдельно в CI.
Docker отсутствует на локальной машине. Проверка GitHub не заменяет деплой BotHost.

`cd apps/mini-app` → `npm ci --ignore-scripts` → `npm test` → `npm run build`.

Из корня: `python -m unittest discover -s tests`. В GitHub добавлен workflow
с frontend/backend проверками, браузерными сценариями, Docker build и проверкой
запуска/сохранения данных после пересоздания Linux-контейнера. Запуск workflow на GitHub и
успешный деплой BotHost должны подтверждаться отдельно, а не фактом push.

Для локального web-only сервера задать `STATIC_DIR=apps/mini-app/dist`,
`WEB_ONLY=true`, `COOKIE_SECURE=false`, `PUBLIC_ORIGIN=http://127.0.0.1:8000`,
`DATA_DIR` отдельной тестовой папкой, затем `python main.py`.
Не переносить локальный `COOKIE_SECURE=false` в production.

Для повторения браузерной проверки из `apps/mini-app`: `npx playwright install chromium`,
запустить `npm run preview -- --host 127.0.0.1 --port 5181`, затем
`node src/storefront/browser-check.mjs` в другом терминале. Скрипт подменяет API
контролируемыми тестовыми ответами и сохраняет снимки в `test-results/storefront`.
Он не создаёт заявки на настоящем сервере и не заменяет сквозной тест CRM/API.
